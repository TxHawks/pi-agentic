## Evidence grades

- **Promised:** README or a public tool description states the behavior.
- **Tested:** A repository test asserts the behavior. Tests use fake processes unless noted.
- **Implementation-only:** The source implements the behavior without a user promise or live proof.
- **Accidental:** The result depends on an incidental detail.
- **Missing:** The repository does not define or test the behavior.

## Time limits

- **Promised:** `timeout` bounds the whole run in whole seconds. `idle-timeout` bounds time without output. Both are unset by default; a child with no budget runs with no limit. [README.md, "Frontmatter reference" (`timeout`, `idle-timeout`)](../../README.md#frontmatter-reference); [README.md, "Time limits"](../../README.md#time-limits).
- **Promised:** `timeout-warn-threshold` reserves the tail of the first threatened limit for reporting. At the threshold, the parent interrupts the child and restarts the same session in report-only mode. `true` means `80%`. One wrap-up phase runs per run. The wrap-up is a normal completion and its session stays resumable. [README.md, "Frontmatter reference" and "Time limits"](../../README.md#frontmatter-reference).
- **Promised:** `on-timeout: report` (the default) keeps `subagent_resume` available after a limit stops the child, and the resumed run gets the same limits. `on-timeout: block-resume` refuses the resume from the model; the operator can still resume from the `/subagents` overlay. [README.md, "Frontmatter reference" (`on-timeout`)](../../README.md#frontmatter-reference).
- **Tested:** The parent watcher kills a child at the hard limit and reports the kill even when the dying child publishes a `done` sidecar. Session growth from child-produced entries keeps a working child alive past the idle budget. A runtime-written prompt does not restart the idle clock. The wrap-up restarts the same session before the original hard deadline and reports the original timeout when the restart spends the reserve. [test/runtime/background-watch-timeout.test.ts](../../test/runtime/background-watch-timeout.test.ts); [test/runtime/interactive-watch-timeout.test.ts](../../test/runtime/interactive-watch-timeout.test.ts); [test/runtime/timeout-budget.test.ts](../../test/runtime/timeout-budget.test.ts); [test/runtime/timeout-wrap-up.test.ts](../../test/runtime/timeout-wrap-up.test.ts); [test/runtime/timeout-result-delivery.test.ts](../../test/runtime/timeout-result-delivery.test.ts).
- **Implementation-only stop:** A timeout kill sends `SIGTERM` to the child process group, then `SIGKILL` after five seconds if the child is still present. The five-second grace is a constant, `TIMEOUT_KILL_ESCALATION_MS`. [src/runtime/timeout-budget.ts#L10](../../src/runtime/timeout-budget.ts#L10); [src/runtime/background-watch.ts#L66-L99](../../src/runtime/background-watch.ts#L66-L99). Escalation is tested with fake processes. [test/runtime/background-watch-timeout.test.ts#L600-L693](../../test/runtime/background-watch-timeout.test.ts#L600-L693).
- **Implementation-only sidecar:** The parent, not the child, writes a `.timeout` sidecar beside the session file after a budget kill. It records the kind (`timeout` or `idle-timeout`), whether the agent's policy blocks a resume, and the budgets the child ran under. A resume clears the sidecar and re-arms the recorded budgets, so a clean later run releases the block and a runaway stays bounded. [src/session/timeout-sidecar.ts](../../src/session/timeout-sidecar.ts); [src/runtime/resume-service.ts#L313-L317](../../src/runtime/resume-service.ts#L313-L317); [src/runtime/resume-service.ts#L402-L438](../../src/runtime/resume-service.ts#L402-L438); [test/runtime/resume-timeout-guard.test.ts#L147-L196](../../test/runtime/resume-timeout-guard.test.ts#L147-L196).
- **Implementation-only ordering:** The wall-clock budget is checked before the idle budget, so a child that spends both in one tick is reported against the run-wide bound. Progress is session-file growth from assistant or tool-result entries only; steers the runtime sends to the child do not count. For an idle wrap-up, the hard deadline is pinned: wrap-up output does not buy a fresh idle interval. [src/runtime/timeout-budget.ts#L27-L41](../../src/runtime/timeout-budget.ts#L27-L41); [src/runtime/timeout-budget.ts#L68-L92](../../src/runtime/timeout-budget.ts#L68-L92); [src/runtime/timeout-budget.ts#L100-L117](../../src/runtime/timeout-budget.ts#L100-L117).
- **Implementation-only wrap-up shape:** The report-only continuation runs with forced auto-exit, all spawning tools denied, context warnings off, and a prompt that forbids new work. Interactive wrap-up closes the old pane and opens a replacement pane on the same session. [src/runtime/timeout-wrap-up.ts#L114-L135](../../src/runtime/timeout-wrap-up.ts#L114-L135); [src/runtime/timeout-restart.ts](../../src/runtime/timeout-restart.ts).
- **Promised limitation, missing enforcement:** Under `parent-close-policy: continue`, a surviving child is intentionally detached. The README says strict enforcement is no longer guaranteed after the parent exits. The clocks live in the parent watcher; no other process takes them over. An abandoned child with a budget runs unbounded until it finishes on its own. [README.md, "Time limits" (last paragraphs)](../../README.md#time-limits); [src/runtime/shutdown.ts#L71-L82](../../src/runtime/shutdown.ts#L71-L82).

## Spawn controls

- **Promised:** `spawn-depth` (default `1`) is a per-level allowance that drops by one at each launch and never rises. A child left with `0` gets no launching tools. `spawn-width` caps a child's simultaneous subagents; a hard ceiling of 16 always applies. `visible-to` (default `all`) limits who may launch an agent: `all`, `root`, or a name list. The env variables `PI_SUBAGENT_SPAWN_DEPTH` and `PI_SUBAGENT_SPAWN_WIDTH` set global ceilings; an agent file can tighten them but never raise them. These are guardrails, not a sandbox. [README.md, "Frontmatter reference" and "Spawn guardrails"](../../README.md#frontmatter-reference).
- **Tested:** The pure policy is tested: whitelist, `visible-to`, and budget refusals each report their failing side; the child budget is the minimum of the target depth, the caller budget minus one, and the env ceiling. The width semaphore is tested: the 16-slot backstop, refusal with a kill remedy at the live limit, rejection of an oversized batch before any launch, rollback of unlaunched reservations, and slot release through completion routing. [test/spawn/policy.test.ts](../../test/spawn/policy.test.ts); [test/runtime/spawn-width.test.ts](../../test/runtime/spawn-width.test.ts); [test/agents/spawn-fields.test.ts](../../test/agents/spawn-fields.test.ts); [test/agents/roster-filtering.test.ts](../../test/agents/roster-filtering.test.ts).
- **Implementation-only fail-closed parsing:** A present but malformed spawn budget parses to `0`, so a bad value never widens a grant. A missing budget means the root default (unbounded). A malformed env ceiling is treated as absent. [src/spawn/policy.ts#L56-L64](../../src/spawn/policy.ts#L56-L64); [src/spawn/policy.ts#L48-L54](../../src/spawn/policy.ts#L48-L54).
- **Implementation-only width scope:** The width semaphore is in-memory state in one parent process (`liveSlotCount` in module scope). The 16-slot ceiling bounds one parent, not the machine. A resume serializes `PI_SUBAGENT_SPAWN_WIDTH_EFFECTIVE` so the resumed child enforces its own frontmatter width. [src/runtime/spawn-width.ts#L1-L5](../../src/runtime/spawn-width.ts#L1-L5); [src/spawn/policy.ts#L190-L196](../../src/spawn/policy.ts#L190-L196).
- **Promised roster limit text, tested:** The ambient roster prints per-agent limit lines — `spawn-depth`, `spawn-width`, `timeout`, `idle-timeout`, `context-warn`, and `report-context-usage: false` — and adds the handling rules only when a listed agent needs them. A context-warn schedule that cannot reach three stages is not shown, because it never instructs a stop. [src/agents/agent-list.ts#L121-L154](../../src/agents/agent-list.ts#L121-L154); [test/agents/roster-limit-fields.test.ts](../../test/agents/roster-limit-fields.test.ts).
- **Implementation-only refusal text:** An oversized batch fails with "batch of N subagents exceeds the spawn width limit of L". A launch at the live limit fails with the busy-slot count and the remedy: wait, or use `subagent_kill` to free a slot. [src/tools/subagent-tools.ts#L133-L139](../../src/tools/subagent-tools.ts#L133-L139).

## Context warnings

- **Promised:** `context-warn-threshold` (`1%`–`99%`, default off) sends the child a wrap-up warning when its context window reaches the threshold, with two more warnings at each `context-warn-step` (default `5%`, minimum `1%`). A warning above 99% moves down to 99%. Only the third stage tells the child to stop; a schedule that cannot reach three stages warns but never blocks. `report-context-usage` (default `true`) adds the child's final context use to the parent result; `false` hides the counts but still reports an instructed early stop. [README.md, "Frontmatter reference" and "Context warnings"](../../README.md#frontmatter-reference).
- **Tested:** The warning schedule, the hold-and-release rule (a warning is held while usage stays at or above its threshold and released on a drop), the completion marker, the final-usage line, and both resume guards are unit tested. [test/tools/subagent-context-reminders.test.ts](../../test/tools/subagent-context-reminders.test.ts); [test/session/completion-reason.test.ts](../../test/session/completion-reason.test.ts); [test/runtime/final-context-usage.test.ts](../../test/runtime/final-context-usage.test.ts); [test/runtime/resume-context-guard.test.ts](../../test/runtime/resume-context-guard.test.ts).
- **Implementation-only stop notice:** When the child stopped as instructed, the parent result appends: the stop was policy-driven, a short report is expected, and the parent must not resume the session. A failed child does not get this reassurance. The session path is hidden from the model for a context-warned result and for a `block-resume` timeout result, so the model cannot route around the guard with a shell. [src/runtime/final-context-usage.ts#L28-L44](../../src/runtime/final-context-usage.ts#L28-L44); [src/runtime/final-context-usage.ts#L55-L84](../../src/runtime/final-context-usage.ts#L55-L84).
- **Tested resume refusal:** `subagent_resume` refuses a session whose last completed run ended under context pressure: "its context window is spent... Launch a fresh sub-agent with the remaining work instead." The operator overlay path can still resume the same session. The marker walk follows the active branch, so a later clean run releases the block. [src/tools/resume-tool.ts#L124-L129](../../src/tools/resume-tool.ts#L124-L129); [src/session/completion-reason.ts](../../src/session/completion-reason.ts); [test/runtime/resume-context-guard.test.ts#L84-L126](../../test/runtime/resume-context-guard.test.ts#L84-L126).
- **Implementation-only plumbing:** The policy travels to the child by env variables (`PI_SUBAGENT_CONTEXT_WARN_THRESHOLD`, `PI_SUBAGENT_CONTEXT_WARN_STEP`). The child records the exit reason as a custom completion entry in its own session; the exit sidecar is authoritative for a `--no-session` child. [src/tools/context-reminders.ts#L1-L2](../../src/tools/context-reminders.ts#L1-L2); [src/runtime/final-context-usage.ts#L99-L104](../../src/runtime/final-context-usage.ts#L99-L104).

## Auto-exit takeover

- **Promised:** Once the operator interrupts (Escape) or sends input to an `auto-exit: true` child, auto-exit is permanently disabled for that session. The child warns the operator and stays open. `/auto-exit` inside the child re-arms it: the next normal completion closes the child. Background children never receive operator input and are unaffected. [README.md, "`auto-exit`"](../../README.md#auto-exit).
- **Tested:** The disable latch notifies once, at the disable moment. Extension-sourced recovery nudges and the initial task never count as takeover. The one-shot re-arm is consumed by a fresh interactive prompt but survives queued steers, and consuming it does not notify again. [test/tools/subagent-done-autoexit-notify.test.ts](../../test/tools/subagent-done-autoexit-notify.test.ts); [test/auto-exit.test.ts](../../test/auto-exit.test.ts); [test/launch/autoexit-persistence.test.ts](../../test/launch/autoexit-persistence.test.ts).
- **Implementation-only notice target:** The takeover notice is a status line and a toast inside the child pane: "Auto-exit disabled — close manually or /auto-exit to re-enable". It goes to the operator, not to the launching parent. [src/tools/subagent-done.ts#L341-L357](../../src/tools/subagent-done.ts#L341-L357).
- **Missing parent notice:** No code path tells the launching parent that the operator took the child over. The parent's watcher keeps waiting until the pane closes. A parent blocked on a taken-over child has no signal about why the result does not arrive. [src/runtime/interactive-watch.ts](../../src/runtime/interactive-watch.ts) (no takeover handling found); searched the full `src/` tree.

## Compatibility gaps to resolve before redesign

1. Abandoned enforcement: after a `parent-close-policy: continue` parent exits, no process owns the child's timeout clocks. The README admits this. Decide whether the next runtime must re-attach and enforce recorded budgets. The `.timeout` sidecar already records budgets, but only after a kill, not at launch for every mode.
2. Parent notice on takeover: the operator's takeover of an auto-exit child is invisible to the launching parent. A parent that waits on such a child waits without a reason. Decide whether takeover must produce a runtime notice to the run's owner.
3. Width scope: the 16-slot ceiling is in-memory per parent process. Two parents on one machine each get 16. State whether the ceiling is per owner or per host.
4. The roster-limits smoke and its benchmark are unwired. Wire them into `package.json` and the README, or delete them.
5. Every timeout, spawn, and context test runs on fake processes. Only one live smoke (Herdr, interactive) covers the wrap-up. There is no live proof of the background `SIGTERM`-then-`SIGKILL` stop or of idle-progress accounting against a real Pi child.
6. The peer range (`>=0.79.x`) is far below the verified Pi 0.84 pin. Either verify the low end or raise the floor.
